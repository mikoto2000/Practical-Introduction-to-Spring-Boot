## 6. Medium Priority Issues

### R-M01: 「文字数」が UTF-16 の長さか見た目の文字数か分からない

- Severity: Medium
- File: `docs/SpringBoot入門/バリデーション入門.md`、`docs/SpringBootテスト入門/バリデーションテスト.md`
- Section / Heading: よく使う制約アノテーション / DTO / DTO のバリデーションテスト
- Line: バリデーション入門63、バリデーションテスト75・400・443
- Category: A 技術的正確性 / D 説明 / G 一貫性 / H 実務
- Issue: String の `@Size` を単に「文字数」と説明し、境界テストも ASCII の反復だけで構成している。日本語の受講者にとって、絵文字・補助文字・結合文字の表示上の長さと同じ仕様だと受け取れる。
- なぜ問題か: 実装は UTF-16 コードユニットの長さを数える。今回、`"😀".repeat(11)` は11コードポイント・String.length() は22で、掲載 DTO の `@Size(max = 20)` による username 違反になることを追加テストで再現した。「20文字以下なら通る」というユーザーへの説明と結果が食い違う。BCrypt のバイト上限、業務ログのコードポイント上限との単位の差も学習上重要である。
- 改善案: 基本説明に「String の @Size は String.length() の単位。見た目の文字数や UTF-8 バイト数ではない」と短く加え、ASCII の境界テストに補助文字1ケースを添える。見た目の文字数を仕様にする場合の独自制約は発展扱いにする。
- 根拠: [Jakarta Size API](https://jakarta.ee/specifications/bean-validation/3.0/apidocs/jakarta/validation/constraints/size)、[Java 21 String API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html#length())、今回の実行結果。

### R-M02: 経過時間を壁時計の差で計測している

- Severity: Medium
- File: `docs/SpringBoot入門/ロギング入門.md`
- Section / Heading: アクセスログ / AOP / MDC の追加 / パフォーマンスログ
- Line: 226・239、351・357・366、483・496、947・952
- Category: A 技術的正確性 / E コード / H 実務
- Issue: 処理時間をすべて `System.currentTimeMillis()` の差で求める。時刻表示のための時計と、所要時間のための時間源の違いを説明していない。
- なぜ問題か: 壁時計の時刻が補正されると、処理の所要時間を正しく表せない可能性がある。時間を監視・閾値判定へ使う例があるので、短い演習の測定でも適切な API を教えた方がよい。今回、時計補正による負値を実際に再現したという指摘ではない。
- 改善案: 開始・終了差分を `System.nanoTime()` に統一し、ログ用には `TimeUnit.NANOSECONDS.toMillis(...)` へ変換する。ログイベントの日時は Logback に任せる、と役割を1文で区別する。
- 根拠: [Java 21 System.nanoTime API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/System.html#nanoTime()) は同一 JVM 内の経過時間を測る用途と使用例を示している。

## 9. ページ横断の問題

### 用語・表記

文字列の「文字数」は @Size の UTF-16、ログのコードポイント、BCrypt のバイト数を区別する（R-M01）。単体テストの依存の扱いは定義・表・用語集で統一する（R-M05）。Flyway の「V1・V2」は概念的な呼称か実ファイル名か明示する（R-M03）。JUnit Jupiter / JUnit 6、Java 21、Boot 4 の表記は改善済みである。

### 重複

各章の対象読者、準備、構成表は独立して読み直すために有用。共通の準備は学習ガイドへリンクされ、同じ長い環境説明を繰り返していない。テストの種類の説明はテスト入門に複数回出るが、意味が揃っていることを優先して修正し、不要な重複を大量に削除する必要はない。

### 矛盾

重大な章間矛盾は確認しなかった。エラー章の ProblemDetail とバリデーションテストの独自 JSON は別プロジェクトの契約として記されている。DB 制約違反の500は演習専用で、業務上の409と無条件に同一視していない。Security のリンク非表示と URL のアクセス拒否も明確に分けられている。

### 前提知識

テスト入門→ケース設計→バリデーションテスト、DB アクセス→統合テスト、Security→Security テストの接続は明確。既存 ZIP と新規 Initializr のサンプルは別プロジェクトとして案内されている。Flyway の追加演習で本編から離れる際の開始状態だけ補う（R-M03）。

### ページ順序

導入・一覧・サイドバーが揃い、前回の順序問題は解消している。全ページ通読後に確認した結果、今回並べ替えを提案する必要はない。基本編と発展編の内容は R-M04 の範囲で調整する。

## 10. 不足している説明

優先度付きの修正は第6・7節にまとめた。以下はそれらを補う短い説明として追加するとよい。

- 入力仕様の長さは、UTF-16・コードポイント・表示上の文字・バイトのどれを使うか決める。
- 時刻と経過時間の役割を分け、ログの日時と duration は別の情報であると説明する。
- 演習の途中から別 DB・別採番へ移るなら、開始状態と終了時の状態を明示する。
- ログのプロファイル例には有効化方法と、期待されるログ1行を添える。
- モックを使う理由は外部依存や再現性の制御であり、単体テストの名称の条件にしない。

Security の入力検証、省略した本番運用、Testcontainers の Docker 前提、実 HTTP と MockMvc の差は既に説明されているため、同じ不足として再掲しない。

## 12. 削減または Appendix 化を推奨する内容

画面共有の基本回では、既に折りたたんだ完成ファイルを講師が全行説明しない。配置は受講者の事前作業にし、入力・処理・観測結果へ時間を使う。

## 15. 良い点

- API の入力、HTTP の契約、DB の保存結果を別々に確認する学び方が一貫している。
- DB の登録失敗だけでなく、削除の途中失敗と復元を検証する演習は、トランザクションの価値を具体的に伝える。
- Security テストは「拒否された」だけで満足せず、認可と CSRF の理由を分け、実ログインと模擬認証も区別している。
- 教材と本番の差を具体的に記し、固定パスワード、入力検証の省略、Docker の実行条件を隠していない。
- 見出し、学習順、折りたたみ、代替テキストが改善され、社内の画面共有と受講者の復習の両方で参照しやすい。
- 既存レビューと修正記録を分離して保存しており、今回の再評価でも改善内容と新しい指摘を追跡できる。
